📦 Distributed Systems Pattern

Transactional Outbox Pattern

Guarantees at-least-once event delivery by atomically writing events to an outbox table alongside business data, then relaying them to the message broker.

💳
Step 1 · Trigger
Payment Success
User checkout completes. The payment service receives a confirmed transaction and needs to notify downstream services.
POST /payments status: PAID orderId: #8821
BEGIN TRANSACTION
🐘
Step 2 · Persistence
PostgreSQL
Both the orders table update and the outbox insert happen in a single atomic transaction — no dual-write problem.
orders table ACID atomic commit
INSERT INTO outbox
📬
Step 3 · Relay Buffer
Outbox Table
A dedicated outbox table holds unpublished events. A poller or CDC tool (Debezium) reads status = PENDING rows.
status: PENDING Debezium / Poller idempotency_key
PUBLISH MESSAGE
🐇
Step 4 · Broker
RabbitMQ
The relay publishes to an exchange. A durable queue ensures messages survive broker restarts. Publisher confirms guarantee delivery.
exchange: payments routing: order.paid durable queue
CONSUME & ACK
⚙️
Step 5 · Handler
Order Consumer
Consumes the order.paid event, triggers fulfilment, marks outbox row PROCESSED, and sends ACK.
manual ack idempotent handler status: PROCESSED
